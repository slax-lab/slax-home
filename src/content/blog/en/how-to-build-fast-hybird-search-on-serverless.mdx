This post is about how we danced on a tightrope: rewriting and optimizing the project until the search API takes only 1.5–2 seconds, back-end request P99 latency dropped sharply, and our fragile D1 got a whole new lease on life. We did not replace a single algorithm along the way: BM25, vector search and RRF are all still there. What made the difference was putting a few Cloudflare capabilities in the right places: Placement to pin execution regions, Service Bindings for cross-region parallelism, D1 query plans, the lifecycle of WASM inside a Durable Object, and per-Worker bundle sizes.

## How the first version worked

Slax Reader got search early, around the end of 2024. Reader had only just launched, and partly for fun and partly as a technical experiment, I built a prototype over a weekend. The idea was simple: stay on the Cloudflare Workers architecture as much as possible. D1 is SQLite underneath and supports FTS5 full-text search, Vectorize handles vector search, and RRF merges the two result lists. A search took four or five seconds, which was acceptable, so nobody touched it again.

The real story starts this month. Our monitoring showed D1 frequently returning `D1 DB is overloaded`, and API latency across the whole site had gone up noticeably. Following the principle of fixing the basic experience first, we started a long round of investigation and rewriting.

```text
Search keyword
   │
   ├─ Jieba segmentation → D1 FTS5 / BM25 ─┐
   │                                       ├─→ Merge by bookmark_id → RRF (K = 60)
   └─ Jina embedding → 5 Vectorize shards ─┘
```

### Jieba word segmentation

> The following is reconstructed from code history and human 🧠 memory, so it may differ somewhat from what actually happened.

Word segmentation is the core of full-text search, and Jieba is the usual choice for Chinese. But Slax Reader is serverless, so it can't just load a segmenter into memory the way a long-running process would, and calling an external segmentation API would add even more things outside our control.

After some research, we chose [the Rust port of Jieba](https://github.com/messense/jieba-rs), compiled to [WASM](https://github.com/fengkx/jieba-wasm), bundled into the Worker and run inside a DO (Durable Object). That sentence sounds easy today, and an agent would get it done quickly. But back when AI wasn't very smart yet, and documentation for Workers, similar open-source projects and outside resources were all scarce, this was a hot potato.

The first problem was how to load the WASM. jieba-wasm only ships what wasm-bindgen generates, which by default locates the file with `new URL('jieba.wasm', import.meta.url)` and then fetches it with `WebAssembly.instantiateStreaming()`. Neither works in a Worker: there's no location to fetch a `.wasm` file from, and [`instantiateStreaming()` isn't supported](https://developers.cloudflare.com/workers/vite-plugin/reference/non-javascript-modules/).

In the end we added a `CompiledWasm` rule to the Wrangler config, so the `.wasm` is compiled into a `WebAssembly.Module` at deploy time, imported directly in code, and passed to `WebAssembly.instantiate()`:

```toml
[[rules]]
type = "CompiledWasm"
globs = ["**/*.wasm"]
fallthrough = false
```

Changing how it loaded had knock-on effects. The bundle grew, the JS glue code generated by `wasm-bindgen` could no longer be used, and the package's TypeScript types were broken too ([fengkx/jieba-wasm#5](https://github.com/fengkx/jieba-wasm/issues/5)). The only option was to copy the glue code line by line into the `SlaxJieba` Durable Object.

How to write a string into WASM memory, how to read segmentation results back out of an `externref` array, how to free memory afterwards: all told it came to more than 300 lines. Some of the imported function names carry hashes generated by `wasm-bindgen`, such as `__wbg_new_1e7c00339420672b`, so they stop matching as soon as `wasm-bindgen` is upgraded. The only option was to pin the version.

The good news was that it worked. The bad news was memory. Each Worker and Durable Object isolate has only [128 MB of memory, counting the JS heap and WASM together](https://developers.cloudflare.com/workers/platform/limits/). Jieba's full dictionary has over 340,000 entries. Compressed and embedded in the WASM, the file is about 3.7 MB, but once loaded it takes up more than 90 MB. Cloudflare's examples instantiate WASM in global scope; we had to do the opposite, putting it inside a Durable Object and loading it only on the first call, or cold starts would time out.

I still remember it as the first time in my life I wrote code like an old-school Nintendo game engineer, scrimping on memory and space in every sense. We even forked `jieba-rs` to change each entry's word frequency from `usize` to `u32` and its part-of-speech tag from `String` to `SmallString`. Most part-of-speech tags are only one or two characters, so this avoids a separate heap allocation for every entry.

Even so, memory kept growing. We couldn't find the cause at the time, so we just contained it: throw away the instance and reload whenever WASM memory went over 120 MB, add a lock to prevent duplicate initialization under concurrency, and spread requests randomly across 20 Durable Objects so each instance would grow more slowly. The code still has a commented-out `idFromName('0')`, which is how it looked when we used just one instance. We only figured out why memory kept growing during this investigation; more on that later.

### Full-text search

After all that work getting Jieba running, we could finally start on full-text search. So that a single query could return the original text for keyword highlighting, Slax Reader stores both the original text and the segmented text in the `slax_bookmark_raw` table, and an FTS5 table is kept in sync with triggers.

The first version of full-text search had a big problem, serious enough that it could have sunk the whole full-text approach. When FTS5 runs `MATCH`, it computes matches across the entire index. Every user's articles live in the same table, and D1 bills by rows scanned. If we simply wrote "MATCH first, then filter by user," every search would scan the whole site's data, getting slower and more expensive as the user base grew.

We tried a lot of different queries at the time, even had an agent read through SQLite's source code, and analyzed everything with `EXPLAIN QUERY PLAN`. In the end we chose to use a CTE to pull out the current user's few dozen rows, then JOIN that against the FTS table. The upside of this approach is that it completes the `MATCH` without a full table scan. The downside is that the `IN` list can hold at most 50 IDs; beyond that, the query plan falls back to a full table scan. (Back when AI wasn't that smart, this was the best that human intelligence plus artificial intelligence could come up with.)


```sql
WITH filtered_ids AS (
  SELECT DISTINCT r.id, r.bookmark_id, r.raw_content, r.raw_title
  FROM slax_bookmark_raw r
  WHERE id IN (/* at most 50 row IDs */)
)
SELECT f.bookmark_id, bm25(slax_fts_bookmark) AS score,
       snippet(slax_fts_bookmark, 0, '[highlight]', '[/highlight]', '...', 32)
FROM filtered_ids f
JOIN slax_fts_bookmark ON slax_fts_bookmark.rowid = f.id
WHERE slax_fts_bookmark MATCH ?
```

So each user's articles were split into groups of 50, one SQL query per group, and more articles just meant a few more concurrent queries. Back then most users had only tens to a few hundred articles, so a handful of concurrent queries was nothing for D1. After all, the rows scanned weren't the whole table, and the query was using the index correctly.

```text
- CO-ROUTINE filtered_ids
- SEARCH r USING INTEGER PRIMARY KEY
- SCAN slax_fts_bookmark VIRTUAL TABLE INDEX 0:M2
SCAN f
```

## D1 starts to overload

The nightmare started with an anomaly in our log summaries. When a bright red `D1 DB is overloaded` keeps showing up in the logs, the problem has become an availability problem.

Take a test account with 619 searchable bookmarks: one search has to be split into 13 batches. Going by the numbers above, searching for "AI" reads close to 30 million rows across those 13 batches.

When all 13 batches go out at once, D1 returns an error: `D1 DB is overloaded. Too many resources consumed within a 10 second window`. Here are the production AI Worker logs from the evening of November 23:

| Keyword | AI Worker time | Full-text search | Semantic search |
| --- | ---: | ---: | ---: |
| 阅读 ("reading") | 8,494 ms | 7,209 ms | 1,927 ms |
| AI | 8,468 ms | 7,515 ms | 1,013 ms |
| cloudflare worker | 1,535 ms | 476 ms | 493 ms |

Almost all the time goes to full-text search. Measured with curl from the client, the same keyword gave a different result every time: four runs of "阅读" took 2.6, 9.1, 10.5 and 14.5 seconds; "cloudflare worker" took about 2 seconds three times and 12 seconds the fourth. Whether a request was fast or slow depended on whether it hit a D1 overload.

Worse, the rejected batches were silently dropped by `Promise.allSettled`, with no error at all. The API still returned 200, just with a lot of full-text results missing, and nobody noticed.

While investigating we also ran into an FTS5 bug: using `(title:NEAR(...)) OR (content:NEAR(...))` together with `snippet()` raises `SQLITE_CORRUPT_VTAB`. Any keyword that segments into two or more words produces exactly this expression, so those batches had been failing all along without anyone noticing. The data itself is not corrupted; you can reproduce it by inserting two rows into an empty in-memory database.

## The rewrite

### Optimizing full-text search

The problem with the old query was that ranking and fetching the original text happened in the same SQL statement. Every group had to carry the full original text through the match, yet in the end only a few dozen characters were used for highlighting. And to keep the query plan from falling back to a full table scan, candidate IDs could only be put into `IN (...)` 50 at a time, so more articles meant more queries.

The idea behind the new approach is to split these two jobs apart: first rank all candidates with one SQL statement that returns only scores, then fetch the original text only for the few dozen results that will actually be shown.

**Step one: rank only.** All of the user's candidate row IDs are packed into one JSON array and passed in as a single parameter, which the SQL expands with `json_each`:

```sql
SELECT r.id AS row_id, r.bookmark_id, bm25(slax_fts_bookmark) AS score
FROM slax_bookmark_raw r
JOIN slax_fts_bookmark ON slax_fts_bookmark.rowid = r.id
WHERE slax_fts_bookmark MATCH ?
  AND r.id IN (SELECT value FROM json_each(?))
ORDER BY score ASC, r.id ASC
```

However many articles a user has, the candidate IDs take up a single bound parameter, so D1's limits of 100 parameters and 100 KB per statement are never reached. The query plan now looks like this:

```text
SCAN slax_fts_bookmark VIRTUAL TABLE INDEX 0:M2
LIST SUBQUERY 1
  SCAN json_each
CREATE BLOOM FILTER
SEARCH r USING INTEGER PRIMARY KEY (rowid=?)
```

It runs one `MATCH` over the FTS index and builds a Bloom filter from the candidate IDs expanded by `json_each`. Each hit is checked against the filter first, then the row is looked up in the original-text table by primary key. The co-routine from the old query is gone. The number of rows read is roughly "the keyword's matches across the whole database + the number of candidates," and has little to do with how many articles the user has.

**Step two: fetch text only for the top 50.** After ranking, only the top 50 results get highlights and full original text; the rest get only a short prefix. Highlights are fetched with two separate SQL queries, one for the title and one for the body, and each one matches only a single column:

```sql
-- Body highlight
SELECT r.id AS row_id,
       snippet(slax_fts_bookmark, 0, '[highlight]', '[/highlight]', '...', 32) AS snippet
FROM slax_bookmark_raw r
JOIN slax_fts_bookmark ON slax_fts_bookmark.rowid = r.id
WHERE slax_fts_bookmark MATCH ?   -- expression that matches only the content column
  AND r.id IN (SELECT value FROM json_each(?))
```

This sidesteps the FTS5 bug above: the two-column `(title:NEAR(...)) OR (content:NEAR(...))` expression is used only for ranking, and ranking only calls `bm25()`, never `snippet()`, so the error is never triggered. The three SQL queries (body highlight, title highlight, original text) run concurrently.

Below are D1's built-in production statistics: the same database (the new one after moving to APAC), real requests from all users, with averages for the old code and the new code. The old SQL numbers cover the period after switching to the new database on November 23 and before the release on November 26:

| SQL | Count | Avg. rows read | Avg. D1 time |
| --- | ---: | ---: | ---: |
| Old: batched CTE query (per batch) | 241 | 247,467 | 139.7 ms |
| New: ranking | 143 | 5,766 | 13.2 ms |
| New: body highlight (top 50) | 115 | 6,357 | 17.0 ms |
| New: title highlight (top 50) | 136 | 868 | 1.3 ms |
| New: original text for top 50 | 236 | 108 | 5.0 ms |
| New: prefix for remaining results (only when over 50) | 52 | 327 | 10.9 ms |

Ranking alone, without highlights, takes only 14 ms for "阅读" with 552 hits and returns 37 KB. The old approach read up to 16.7 MB of original text into the Worker at once; now only the top 50 results get original text, about 0.4 MB on average.

## Optimizing the request path

The full-text query is only one part of a search request. Recent logs show that even when full-text search isn't slow, semantic search still takes 0.5–1.9 seconds, and the step before search that segments the keyword and reads the user's bookmark list takes another 0.5–1.1 seconds. So every Worker the request passes through had to be measured. Apart from the full-text query, the problems were in three places: how the Workers were split, where vector search ran, and Jieba segmentation.

### Splitting the Workers

This one started with user reports that access from outside Asia was slow, with the occasional request waiting an extra second or two.

At the time the back end had three Workers: Edge, Core and AI. When we first split them, we hadn't considered that cold starts on Cloudflare could also cause high latency, so all three bundled every dependency: the dependency injection container with its registered classes, all Workflows and Durable Objects, plus Jieba's WASM. Even though Edge only handled authentication and forwarding, its upload was 16 MB, and every cold start loaded the entire back end.

Where the Workers ran was also a problem. We had tried enabling [Smart Placement](https://blog.cloudflare.com/announcing-workers-smart-placement/) for Core before, but overall it turned out to give the worst results, so every Worker had always run nearest to the user.

PostgreSQL is in Singapore, but Core had no pinned location: it ran wherever the user's request came in. Here are 24 hours of production statistics, which make it clear that the extra wall-clock time was spent reaching the database across oceans.

| Data center | Core median time | CPU median |
| --- | ---: | ---: |
| Singapore SIN | 123 ms | 27 ms |
| Hong Kong HKG | 202 ms | 23 ms |
| Tokyo NRT | 304 ms | 23 ms |
| Los Angeles LAX | 620 ms | 25 ms |
| Frankfurt FRA | 589 ms | 31 ms |
| US East IAD | 793 ms | 29 ms |

Cloudflare already has a recommended pattern for this. When it launched Smart Placement in 2023, the docs suggested splitting a full-stack app into two Workers: a front-end Worker that stays near the user and handles authentication and routing, and a back-end Worker with Placement enabled that runs near the database, with the two connected by a Service Binding. But because Smart Placement had made things worse for us, we never turned it on.

Workers Cache, released on July 6 this year, added a caching layer on top. The architecture Cloudflare describes is:

```text
User
  ↓
Worker A: near the user, auth, rate limiting, routing
  ↓ Service Binding
Worker B's Workers Cache
  ├─ Hit: return directly, B doesn't run
  └─ Miss: Worker B runs near the data, queries the database and writes to the cache
```

In this update, Workers Cache wasn't actually the most important part for us. What mattered was that pinning where a Worker runs was finally released. Before, the only options were "run nearest to the user" and "Smart Placement"; now you can pin execution to a specific data center location, and I could finally pin the business-logic and data Workers to `ap-southeast-1`. Following that idea, we ended up with six Workers:

| Worker | Responsibility | Location |
| --- | --- | --- |
| Edge | CORS, auth, rate limiting, routing, image proxy | Near the user |
| Core | General API, queues, cron jobs, Workflows | Singapore |
| AI | Search, recommendations, AIGC | Singapore |
| Objects | Jieba, WebSocket and screenshot Durable Objects | Singapore |
| Vector | Jina embedding, vector retrieval | US |
| Browser | Browser rendering | Near the user |

We didn't use Workers Cache because search requests all carry an `Authorization` header, which bypasses the cache by default. Even without that, every user and every keyword is a different cache key. So the speedup this time came from changing the queries and adjusting where things run, not from caching.

After the split went live, we ran into another Cloudflare behavior: Placement only applies to `fetch`, and RPC calls run in the caller's data center. So we had to change Edge to forward requests with an internal Worker secret, so that each Worker would actually run in the location we intended.

### Slimming down the Workers

For this part, we had AI scan the code to determine which dependencies each Worker actually used, then trimmed each one accordingly.

- Registration code for dependency injection, routes, queues and cron jobs is generated separately per Worker, so each Worker includes only the classes it uses.
- AI routes were split into their own small controllers, so they no longer pull in all of Core's dependencies.
- Heavy libraries such as `defuddle` and email MIME parsing are now loaded only when used.
- `moment-timezone` was replaced with `date-fns`.
- Zod, used in only one place, was replaced with hand-written validation.
- The unused MCP service was removed.

Below are medians from 7 local runs of `wrangler check startup`. The numbers aren't the same as in production; they're mainly for comparing before and after:

| Worker | Cold start time | Upload size |
| --- | ---: | ---: |
| Edge | 262 → 24 ms | 16 MiB → 89 KiB |
| Core | 233 → 96 ms | 16 MiB → 9.9 MiB |
| AI | 272 → 68 ms | 16 MiB → 5.9 MiB |
| Objects | 23 ms | 4.0 MiB |
| Vector | — | 44.8 KiB |

After these changes, back-end latency held steady at P50 247 ms and P90 368 ms. Cause for celebration.

### Moving vector search to the US

<UrlCard
	href="https://blog.cloudflare.com/building-vectorize-a-distributed-vector-database-on-cloudflare-developer-platform/"
	title="Building Vectorize, a distributed vector database, on Cloudflare's Developer Platform"
/>

> "Vectorize runs in every Cloudflare data center, on the infrastructure powering Cloudflare Workers."

> "Each query is processed on a server in the data center in which it enters … The Vectorize DB Service … processes the query by reading the data for that index on R2 … through Cloudflare's Cache."

> "When used via a Worker binding, each query is processed close to the server serving the worker request, and thus close to the end user."

Until then I had taken Cloudflare's description at face value, so Jina embedding and Vectorize queries both ran alongside Core. But just as a "fact" in the legal sense and what objectively happened are two different things, Vectorize queries work the same way: the query really does run nearby, but the data source is still in the US, so it still has to cross the ocean.

| Step | Singapore | US |
| --- | ---: | ---: |
| Jina embedding | 278 ms | 81 ms |
| Vectorize query, 50 results with vectors | 978 ms | 213 ms |
| Total | ~1.26 s | ~0.29 s |

More than four times faster. So we added a Vector Worker pinned to `aws:us-east-1`. It does exactly one thing: given a keyword and a user ID, it calls Jina to generate the vector, queries Vectorize, rescores against the platform mean, and returns a list of candidates.

Now, when a search request comes in, the semantic request is sent to the US right away. Without waiting for it to return, Singapore carries on with segmentation and full-text search, and the two are merged once both finish. After merging, a quick PostgreSQL query confirms the user owns each article and that it hasn't been moved to the trash.

### Fixing Jieba

Once everything above was changed and tested, it was time to face the most complicated part: Jieba in Rust WASM.

Earlier, to keep the DO from erroring and restarting all the time, we had made up a rule on the spot: 20 instances per region. It did run as smoothly as we hoped for a long time; it's just that 99% of the time, every request had to pay the cold start cost for it.

300 ms is nothing in the span of a lifetime, gone in the blink of an eye. But when it happens inside a request, the user behind that HTTP request gets irritated, waits, feels uneasy. That's bad. Very bad.

So why 20 instances? Because Jieba's memory kept growing, and back then neither the human nor the AI was fluent in Rust, so we could only cover up an ugly bug in an ugly way. Fortunately it's 2026 now.

My AI took just three minutes to tell me that the old WASM used the `wee_alloc` allocator, which can't reclaim freed memory under this workload, so memory grows by roughly 0.8 MB for every 16 KB of text processed. That was a great find, and it even dug up the `wee_alloc` issue to show me that the problem is still unresolved.

Once the problem was known, the fix was simple. In our fork of `jieba-wasm`, we removed `wee_alloc` in favor of `dlmalloc`, the Rust standard library's default allocator on `wasm32-unknown-unknown`, and rebuilt. The dictionary is still the same complete one. Comparing the old and new builds' segmentation of the full text of *Fortress Besieged*, memory held steady at about 57 MB and stopped growing. The rest of the changes were even simpler: load the WASM only once per isolate, send all requests to the same Durable Object, remove the lock and the rebuild logic, and process long text in 32 KB chunks.

After the change, measuring again in the test environment, only 2 of 43 calls were cold starts, both of them the first load after a deploy.

## Looking back

I like to tinker, but until now I had always believed that doing something as complex as hybrid search well on serverless, with both performance and stability, was close to impossible. External dependencies, algorithms, the flow itself, latency: any one of them could get in the way. Getting it both fast and stable seemed almost impossible without a traditional long-running back-end service.

But this round of search optimization also brought overall back-end latency down to P50 240 ms / P90 368 ms. The recipe of SQLite D1, BM25, vector search and RRF didn't change. Tuning where Placement should put things, tuning where Jina and Vectorize should run, optimizing the D1 full-text SQL, and tracking down the Jieba memory leak made a huge difference to the whole back end. A project really does need someone to keep looking back and keep polishing it, to stay alive.

(The first version's CTE wasn't wrong, either. When there were few articles, it really did save a lot in scan costs. It's just that as more and more data accumulated, the old trade-off had to be recalculated.)
